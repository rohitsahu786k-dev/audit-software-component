# Deploying OnePWS AuditPro

One Render web service runs everything: the Express API **and** the built React
SPA. `client/src/utils/api.js` calls relative `/api` paths, so serving both from
one origin means there is no CORS setup and no API-base URL to configure in the
browser.

## Why not GitHub Pages / Vercel / Netlify

- **GitHub Pages** serves static files only. This app needs a live Node process
  for MongoDB sync, auth, media uploads and email.
- **Serverless platforms (Vercel/Netlify functions)** don't keep a process
  alive. `server.js` schedules the daily CAPA reminder with `node-cron`, and
  that only fires while the process runs.
- **Render's free tier** sleeps after inactivity — the cron would be silently
  skipped. Use the paid `starter` plan (or any always-on host) if the automatic
  reminders matter. If you genuinely don't need them, set
  `EMAIL_AUTOMATION=false` and a sleeping tier becomes acceptable.

## First deploy (Render Blueprint)

1. Go to <https://dashboard.render.com/blueprints> → **New Blueprint Instance**.
2. Connect the GitHub account `rohitsahu786k-dev` and pick
   `audit-software-component`. Render reads [`render.yaml`](render.yaml).
3. Render will prompt for every secret marked `sync: false`. Fill in:

   | Variable | Value |
   |---|---|
   | `MONGODB_URI` | Your Atlas connection string |
   | `SMTP_USER` | Gmail address that sends reminders |
   | `SMTP_PASS` | Gmail **app password**, not the account password |
   | `SMTP_FROM` | e.g. `ONEPWS AuditPro <you@domain.com>` |
   | `CLOUDINARY_URL` | `cloudinary://API_KEY:API_SECRET@CLOUD_NAME` |

   `AUTH_SECRET` is auto-generated by Render — leave it alone.

4. **Allow Render's egress IPs in MongoDB Atlas.** Atlas blocks unknown IPs by
   default, so the first deploy will fail its health check without this. Copy the
   outbound IPs from the Render service's *Connect* tab into Atlas →
   *Network Access*.
5. Deploy. Health check is `GET /api/health`, which returns `200` only after
   Mongo responds — so a green service means the DB is genuinely reachable.

Your live URL will be `https://onepws-auditpro.onrender.com` (Render appends a
suffix if the name is taken — the dashboard shows the real one).

Every later push to `main` auto-deploys (`autoDeployTrigger: commit`).

## Verifying a deploy

```bash
curl https://<your-service>.onrender.com/api/health
# {"ok":true,"ts":"...","version":"2026-07-02","service":"OnePWS-AuditPro"}
```

Then open the root URL and log in. If the page loads but every API call 401s,
the build shipped without a fresh client bundle — check the build log for
`Serving client build from client/dist`.

## Local production check

Reproduce exactly what Render runs, before pushing:

```bash
npm run build:render   # installs both workspaces + builds client/dist
npm start              # server on :3001, serving the SPA too
```

Open <http://localhost:3001> — not `:5173`. If `client/dist` is missing the
server logs `API only` and the root URL returns 404; that is expected in dev,
where Vite serves `:5173` with its own `/api` proxy.

## Environment variables

[`.env.example`](.env.example) is the full list. Locally they live in a root
`.env` (gitignored, never committed). In production they live in Render's
environment settings — do not commit a `.env` to make a deploy work.

Two that matter most in production:

- **`AUTH_SECRET`** — without it, `middleware/auth.js` derives the token-signing
  key from `MONGODB_DB`, which is guessable. Always set a random value.
- **`ALLOWED_ORIGINS`** — leave empty for the single-service setup. An empty
  value means same-origin only. Set it only if you later host the client on a
  separate domain.
